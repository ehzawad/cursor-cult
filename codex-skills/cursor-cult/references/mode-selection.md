# Mode and fleet selection contract

Claude Code or Codex, not the Python runner, chooses roles from the user's current prompt, conversation, live repository evidence, and authority boundaries. Apply this precedence for every role:

1. **User intent and explicit mode.** Honor an explicitly requested `ask`, `plan`, `agent`, read-only, implementation, review, or detached/background preference when it is compatible with the hard constraints.
2. **Authority gate.** This is non-overridable: a role may never use `agent` when writes or command execution were not authorized. A contradictory no-write constraint defeats an `agent` label, and ambiguity defaults to read-only.
3. **Role deliverable.** Use `ask` to inspect, explain, diagnose, review, or gather evidence without mutation. Use `plan` to produce a structured implementation or decision plan without mutation. Use `agent` only when the role must edit files or run locally mutating commands to produce an authorized outcome.
4. **Shell and network capability.** `ask` and `plan` roles are denied `Shell(*)` by default. When command execution is explicitly authorized but file mutation is not, and a role genuinely needs `curl`, `git`, `gh`, a package manager, a test command, or another shell-based network probe, keep the role in `ask` or `plan` and add `--readonly-shell` to the fleet execution. Do not promote a role to `agent` merely to gain network access. Because `--readonly-shell` applies to every non-writer in that invocation and shell can mutate through redirection or mutating programs, isolate such roles in a separate, narrowly scoped fleet whenever practical. The parent Claude Code or Codex sandbox must independently allow the required network; no Cursor flag can widen it.
5. **Independent context test.** Multi-agent is fleet topology, not a Cursor mode. Create another role only for an independently owned question or deliverable that benefits from a separate context window. One role is valid.
6. **Worktree safety.** A shared worktree permits at most one `agent` writer. Concurrent writers require isolated worktrees and separate Cursor Cult invocations; the host may run and watch those invocations concurrently.
7. **Recomposition.** Re-evaluate roles and modes after each material handoff or workspace change. Do not force every task through a fixed ask → plan → agent pipeline.

Foreground/background is a separate lifecycle choice. The same role set can run synchronously with `run` or durably and asynchronously with `start` plus a host-owned watcher. Cursor's own `--background` option is not a more capable substitute for the runner's `-p` stream transport and does not change the capability envelope.

Each role should include a concise `mode_reason` so `check`, detached state, and watchdog events make the host's decision auditable.

This precedence is host discipline, but the default read-only half is machine-enforced. Every non-writer role runs under a Cursor permission configuration denying `Write(**)` and, unless `--readonly-shell` was explicitly selected, `Shell(*)`; Cursor applies deny rules ahead of allow rules and ahead of `--force`. The runner additionally rejects an `agent` role without `--writer`, rejects a `--writer` role not in `agent` mode, rejects more than one writer per invocation, and refuses `ask`/`plan` roles when the CLI does not advertise `--mode`. `--readonly-shell` deliberately relaxes one layer: `Write(**)` remains denied, but shell is a write vector, so the host must not describe that fleet as hard read-only. What remains host judgment is which mode and capability envelope a role deserves; an `agent` role or read-only shell capability you authorize is genuinely authorized within the parent host's remaining restrictions.
